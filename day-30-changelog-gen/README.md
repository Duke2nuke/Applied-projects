# Day 30 — changelog-gen: CHANGELOG.md Generator from Git History (Day C: community / open-source)

A stdlib-only CLI that turns a git repository's history into a
`CHANGELOG.md`, grouped by release (git tags) and sorted into sections
from Conventional Commits subjects (`feat:`, `fix:`, `docs:`, ...).
Anything newer than the newest tag lands under `[Unreleased]`.

## Who would use this, and why

Every open-source project is supposed to ship a changelog, and almost
every small project doesn't have one — maintainers write release notes
by hand, forget, or paste a raw `git log`. This generates the file in
one command from history the project already has, so a maintainer can
run it before every release instead of reconstructing what changed.
It is also useful in CI: generate the changelog, commit it, and the
release notes are done. It needs no dependencies and no GitHub token —
just git and the repo itself.

## Install / run

Requires Python 3.9+ and git. No third-party packages.

```bash
# print the changelog for the current repo
python changelog_gen.py

# write it to a file
python changelog_gen.py --repo /path/to/repo --output CHANGELOG.md

# only releases newer than a tag (e.g. for release notes)
python changelog_gen.py --since v0.1.0

# include merge commits (skipped by default)
python changelog_gen.py --include-merges
```

Run the tests:

```bash
python -m unittest test_changelog_gen -v
```

## Example

Input — a repo with this history (see `examples/CHANGELOG.md` for the
full generated file):

```
v0.1.0
  feat: add login page
  fix: crash on empty password
  docs: rewrite README install steps
Unreleased (after v0.1.0)
  feat(api): add rate limiting
  fix: off-by-one in pager
  feat!: drop Python 3.8 support
```

Output:

```markdown
# Changelog

## [Unreleased]

### Breaking Changes

- drop Python 3.8 support (527f9d9)

### Features

- **api:** add rate limiting (7a2cebe)

### Bug Fixes

- off-by-one in pager (2125aee)

## [v0.1.0] - 2026-11-10

### Features

- add login page (06fe1a0)

### Bug Fixes

- crash on empty password (897e563)

### Documentation

- rewrite README install steps (bf4d9b9)
```

## How it works

1. `git log` returns every commit (newest first) with hash, author,
   date, subject, and body.
2. `git tag` returns tags; each tag is ordered by where its commit
   sits in the log (log position, not tag creation date — same-day
   releases can share a creation date, and log position is the
   reliable order).
3. Walking the log newest-first, a commit belongs to the first tag
   whose tagged commit has been reached; anything before the newest
   tag is `[Unreleased]`.
4. Each subject is parsed as a Conventional Commit:
   `type(scope)!: description`. The type picks the section
   (`feat` -> Features, `fix` -> Bug Fixes, `docs` -> Documentation,
   `refactor`, `perf`, `test`, `chore`, `build`, `ci`, `style`,
   `revert`); anything else goes to Other Changes. A `!` marker or a
   `BREAKING CHANGE:` footer moves the entry to Breaking Changes.
5. Merge commits are skipped unless `--include-merges` is given.

## Results (actually run)

- 13/13 unit tests pass (`python -m unittest test_changelog_gen`).
  Tests build real throwaway git repos and check grouping, the
  Unreleased section, breaking-change detection (both `!` and footer),
  non-conventional subjects, scopes, merge handling, `--since`
  filtering, and error cases (not a repo, empty repo, unknown tag).
- The example in `examples/CHANGELOG.md` was generated by running the
  tool on a real fixture repo — the hashes and dates in it are the
  fixture's, not hand-written.
- One real bug was found by the tests during the build: tags created
  on the same day sorted unpredictably by creation date, so releases
  could be assigned to the wrong version. Fixed by ordering tags by
  log position instead.

## Limits

- Only git repositories work; there is no support for other VCS tools.
- Commit subjects that don't follow Conventional Commits are kept
  under Other Changes, not dropped — but the sections are only as
  good as the commit messages.
- Tags must point at commits in the log; annotated vs lightweight
  tags are both handled via `git rev-list`.
- Commit bodies containing the raw separator characters are
  vanishingly unlikely in practice, but the parser assumes they
  don't appear.
- No GitHub API use: PR numbers and issue links are not resolved —
  only what is already in the commit message appears.

## 2-minute explainer

**Problem:** small open-source projects rarely keep a changelog, so
users can't tell what changed between releases, and maintainers
reconstruct release notes by hand.

**Approach:** a single-file, stdlib-only Python CLI that reads
`git log` and `git tag`, groups commits by release, and sorts them
into sections from their Conventional Commits subjects — features,
bug fixes, breaking changes, and so on — printing Markdown or
writing `CHANGELOG.md`.

**Results:** 13 passing tests over real fixture repos, including the
Unreleased section, breaking changes, scopes, `--since` filtering,
and error handling; the example changelog was generated by the tool
itself. One ordering bug (same-day tags) was caught by tests and
fixed by sorting tags by log position.

**Limits:** it only understands git, and its sections are only as
good as the project's commit messages — non-conventional subjects
land in Other Changes instead of being dropped.
